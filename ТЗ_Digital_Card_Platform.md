# ТЕХНИЧЕСКОЕ ЗАДАНИЕ

## на разработку программного продукта «Digital Card Platform» — сервиса цифровых визиток

*Составлено с учётом ГОСТ 19.201-78.*  
Версия ТЗ: 1.0. Дата: 17.09.2026.

## 1. Введение

Программный продукт (далее — ПП) **Digital Card Platform** представляет собой веб-приложение для создания, редактирования, публикации и распространения цифровых визитных карточек. Пользователь может создавать визитки с персональными и контактными данными, добавлять ссылки на социальные сети, публиковать визитку по постоянному публичному адресу, открывать её в браузере, копировать ссылку и использовать QR-код для передачи профиля.

Область применения — учебная и демонстрационная. ПП используется как самостоятельный веб-проект и как объект функционального тестирования методом «чёрного ящика» в рамках практической работы по дисциплине, посвящённой тестированию программного обеспечения.

## 2. Основания для разработки

Основанием для разработки является учебный проект **Digital Card Platform**, развиваемый как полнофункциональное веб-приложение с клиентской и серверной частью. При подготовке настоящего ТЗ учитываются требования практической работы №1 «Тестирование программного продукта методом „чёрного ящика“».

Нормативная база:

- ГОСТ 19.201-78 «Техническое задание. Требования к содержанию и оформлению»;
- ГОСТ 34.602-2020 «Информационные технологии. Комплекс стандартов на автоматизированные системы. Техническое задание на создание автоматизированной системы»;
- ISO/IEC/IEEE 29148:2018 «Системная и программная инженерия. Процессы инженерии требований».

Исходный репозиторий проекта: `nxstd/digital-card-platform`.

## 3. Назначение разработки

Функциональное назначение ПП — предоставить пользователю простой способ создавать и управлять цифровыми визитками, публиковать их по постоянным URL-адресам и передавать другим пользователям через ссылку или QR-код.

Эксплуатационное назначение — работа в современном веб-браузере с возможностью запуска полного стека локально при помощи Docker Compose либо запуска клиентской и серверной частей раздельно в среде разработки.

Дополнительное учебное назначение — использование специально подготовленной версии ПП для разработки тест-кейсов, поиска и документирования дефектов методом «чёрного ящика».

## 4. Требования к программе

### 4.1. Функциональные требования

| Код | Требование |
|---|---|
| ФТ-1 | Система должна отображать список созданных цифровых визиток и предоставлять переход к созданию новой визитки. |
| ФТ-2 | Пользователь должен иметь возможность создать визитку, указав обязательные поля «Публичный адрес» и «Имя и фамилия», а также необязательные поля: должность, компания, описание, email, телефон, сайт, город и URL изображения. |
| ФТ-3 | Публичный адрес (`slug`) должен состоять из латинских букв нижнего регистра, цифр и дефисов, не начинаться и не заканчиваться дефисом и быть уникальным для каждой визитки. |
| ФТ-4 | Пользователь должен иметь возможность добавлять к визитке произвольное количество ссылок на социальные сети. Для каждой непустой строки соцсети должны быть указаны платформа и корректный URL. |
| ФТ-5 | При удалении одной строки социальной сети должна удаляться только выбранная строка, остальные строки должны сохраняться без изменений. |
| ФТ-6 | Пользователь должен иметь возможность редактировать существующую визитку. После сохранения изменённые данные должны отображаться в списке и на публичной странице. |
| ФТ-7 | Пользователь должен иметь возможность удалить визитку. Перед удалением система должна запросить подтверждение. При подтверждении визитка удаляется, при отмене данные остаются без изменений. |
| ФТ-8 | Поиск по списку визиток должен выполняться без учёта регистра по ФИО, компании, должности и публичному адресу. |
| ФТ-9 | Нажатие на карточку в списке должно открывать публичную страницу по маршруту `/v/{slug}`, соответствующему публичному адресу выбранной визитки. |
| ФТ-10 | Публичная страница должна отображать имя, должность, компанию, описание, город и доступные контактные данные. Отсутствующие необязательные данные не должны создавать пустые элементы интерфейса. |
| ФТ-11 | Ссылка «Почта» должна открывать `mailto:` для указанного email, ссылка «Телефон» — `tel:` для указанного номера, ссылка «Сайт» — URL, сохранённый в поле сайта. |
| ФТ-12 | Ссылки социальных сетей на публичной странице должны открывать соответствующие URL в новой вкладке. |
| ФТ-13 | Для публичной визитки должен формироваться QR-код, соответствующий её публичному URL. |
| ФТ-14 | Кнопка «Скопировать ссылку» должна помещать в буфер обмена точный публичный URL текущей визитки без добавления лишних сегментов или параметров. |
| ФТ-15 | При вводе некорректного email, URL сайта, URL фотографии или URL социальной сети форма должна отклонять сохранение и выводить понятное сообщение об ошибке. |
| ФТ-16 | При попытке создать визитку с уже занятым публичным адресом система должна сообщить о конфликте и не создавать дубликат. |
| ФТ-17 | При обращении к несуществующей визитке система должна отображать корректное состояние «не найдено», не завершая работу приложения необработанной ошибкой. |

### 4.2. Требования к надёжности

- ПП не должен завершаться необработанной ошибкой при типовых пользовательских действиях: создание, редактирование, поиск, удаление, открытие публичной страницы и копирование ссылки.
- Серверная часть должна возвращать согласованные ответы при ошибках валидации, конфликте уникального `slug` и запросе отсутствующей сущности.
- Данные должны сохраняться в реляционной базе данных и оставаться доступными после перезапуска приложения при использовании постоянного тома PostgreSQL.
- Удаление визитки должно удалять принадлежащие ей записи социальных ссылок без появления «осиротевших» данных.

### 4.3. Условия эксплуатации

Для контейнерного запуска требуется Docker с поддержкой Compose. В демонстрационной конфигурации запускаются:

- frontend на Next.js;
- backend на FastAPI;
- PostgreSQL;
- миграции Alembic перед запуском backend.

Для локальной разработки без Docker требуются:

- Python 3.13;
- `uv`;
- Node.js 26 и `npm`;
- современный веб-браузер с поддержкой JavaScript.

### 4.4. Требования к совместимости

ПП должен корректно работать в актуальных версиях Google Chrome, Mozilla Firefox и Microsoft Edge на настольных ОС Windows, Linux и macOS. Интерфейс должен сохранять работоспособность на мобильных и десктопных разрешениях.

Backend предоставляет REST API и не должен зависеть от конкретного браузера. Для основной контейнерной конфигурации используется PostgreSQL; для локальных автоматизированных тестов допускается SQLite.

## 5. Требования к интерфейсу

- Интерфейс должен быть выполнен в едином визуальном стиле и оставаться читаемым на различных размерах экрана.
- Обязательные поля формы должны быть визуально обозначены.
- Пользователь должен видеть живой предпросмотр создаваемой или редактируемой визитки.
- Кнопки создания, сохранения, удаления, добавления и удаления социальной ссылки должны иметь однозначные подписи или доступные `aria-label`.
- Ошибки валидации должны отображаться в интерфейсе понятным текстом.
- При удалении визитки должно отображаться системное подтверждение с названием удаляемой визитки.
- Публичная страница должна содержать отдельный блок «Поделиться» с QR-кодом, отображением публичного URL и кнопкой его копирования.
- При успешном копировании ссылки пользователь должен получить визуальное подтверждение «Ссылка скопирована».

## 6. Критерии приёмки

ПП считается соответствующим настоящему ТЗ, если выполнены функциональные требования раздела 4.1 и успешно проходит не менее 95% разработанных тест-кейсов, включая обязательные сценарии:

1. создание визитки с корректным буквенным `slug`;
2. отклонение некорректных значений `slug`, email и URL;
3. поиск одной и той же визитки запросами в разных регистрах;
4. открытие публичной страницы из списка и проверка соответствия маршрута `slug`;
5. добавление нескольких социальных ссылок и удаление выбранной строки;
6. подтверждение и отмена удаления визитки;
7. проверка ссылок email, телефона, сайта и социальных сетей;
8. копирование публичной ссылки и сравнение значения в буфере обмена с отображаемым URL;
9. проверка QR-кода публичной визитки;
10. обработка дублирующегося `slug` и отсутствующей визитки без необработанных ошибок.

Критические пользовательские сценарии создания, открытия и удаления визитки должны выполняться корректно.

## 7. Требования к документации и порядок запуска ПП

Вместе с ПП передаются настоящее ТЗ и `README.md` проекта. README содержит описание архитектуры, используемых технологий, структуры проекта, переменных окружения, API и способов запуска.

### Запуск через Docker Compose

Из корневой директории проекта выполнить:

```bash
docker compose up --build
```

После запуска по умолчанию доступны:

- frontend: `http://localhost:3000`;
- backend API: `http://localhost:4000`;
- health check: `http://localhost:4000/api/health`;
- Swagger UI: `http://localhost:4000/docs`;
- ReDoc: `http://localhost:4000/redoc`.

### Локальный запуск backend

```bash
cd server
uv sync
uv run alembic upgrade head
uv run fastapi dev app/main.py --host 0.0.0.0 --port 4000
```

### Локальный запуск frontend

```bash
npm ci
npm run dev -w client
```

## 8. Порядок контроля и приёмки

Контроль проводится методом «чёрного ящика». Тестировщик должен использовать требования настоящего ТЗ как источник ожидаемого поведения, не опираясь на внутреннюю реализацию тестируемой версии ПП.

В процессе испытаний выполняются:

- функциональное тестирование;
- позитивные и негативные сценарии валидации;
- проверка граничных и ошибочных входных данных;
- тестирование навигации;
- проверка пользовательских действий с подтверждением;
- проверка ссылок и буфера обмена;
- проверка поведения при конфликте и отсутствии данных.

Обнаруженные несоответствия документируются в виде баг-репортов с идентификатором, названием, предварительными условиями, шагами воспроизведения, ожидаемым и фактическим результатом, серьёзностью и статусом.
